## Recommended delivery order

First close the narrow authentication review and establish the actual candidate. Then fix everyday navigation/search, separate general chat from studio context, simplify entry, and deliver the file library. Prepare committee hosting alongside this work, releasing an initial private review deployment once its own acceptance checks pass. Add scored recommendations and non-software deliverables, then online discovery, bounded unattended orchestration, and successively larger software recipes. Finish with an integrated local/hosted acceptance pass. Retain the wider product and research tracks explicitly rather than treating them as prerequisites for every release.

Use stage gates rather than calendar promises. This project has substantial implemented functionality, but source implementation, fixture checks, installed behavior, current role qualification, and live activation have different evidence. Do not restart T00–T19 or X01–X10 as if nothing exists.

## Product decisions to carry into the designs

### General assistance versus project actions

Keep general chat useful with no project selected. A broad writing, comparison or ideation request must not be silently reinterpreted as “search my CA projects.” General knowledge answers remain labeled as unverified where appropriate; fresh external facts require an explicit research path with citations. General chat need not gain unrestricted tools. Offer a separate action card to use an answer as a discovery brief or other record. Display the context actually sent, and make opt-in project context removable. No general assistant access in frozen human-only study workspaces.

### Defaults and onboarding

Offer Guided and Advanced views over the same workflow, not two implementations. Default to a manual start, qualified permitted connections, current user ceilings, newest records and a clear output choice. Show “what will happen” and effective limits before starting; display unconfigured necessities as blockers. Copying defaults must never fabricate claims, model qualification, ethical review, signatures or grants. Preserve the accepted Economy/Quality/Local-only/fixed-model choices. Prefer ordinary defaults and saved project presets over a large new configuration framework.

### Automatic scoring and response type

Reuse `context/SCORING_RUBRIC.md` and the selection engine. The system proposes criterion ratings and evidence-linked explanations; deterministic code computes aggregates and gates selection. Missing evidence remains unknown. Human edits create an attributable assessment/override version without overwriting system ratings. Re-evaluate when the supporting evidence or candidate changes.

The cross-option suitability rubric must determine software versus existing-tool/process/human/hybrid/proposal recommendations; software influence is descriptive in that comparison. Rank eligible, sufficiently supported options rather than blindly building the maximum numeric total. If two leaders remain unresolved, use a bounded validation/research step or an honest pause. Explain how a software component could help when supported, while retaining the better non-code option.

### “Approve for me” and unattended operation

The UI can say “Approve routine steps for me,” backed by a deterministic scoped policy, not a model impersonating the owner. Configure allowed research, evidence admission, selection, spec freeze, isolated build/review/repair and private packaging; time/call/spend/quota caps; domains/data classes; output families; and stop conditions. Show one reviewable policy summary and reuse matching grants. Reuse existing oversight records and immutable run modes. Do not add per-step confirmations for actions already covered.

Current owner-reviewed claim admission must gain a separately recorded policy path before unattended claims count as accepted evidence. Store extraction, quote/source validation and policy admission separately; a model's confidence does not establish truth or independent corroboration. Changed material scope requires a new policy version. Publishing, campaigns, account changes and purchases require matching authority; do not introduce blanket fresh approvals for operations already covered. Preserve human-only denials and fixed study conditions.

### Preview lifetime

Distinguish preview access lifetime, a running server/session, and individual process execution limits. “Until I close it” is a selectable session mode; an open preview keeps its lease, Stop revokes immediately, and disconnects get a documented reconnect grace period. Browser unload is unreliable, so a last-viewer heartbeat/lease must clean up abandoned work. Multiple viewers, sleep, crash and reconnect must have explicit behavior. A short-lived ticket may still expire and renew without stopping the preview. Manual-stop must not remove CPU, memory, network, concurrency or financial caps. Generated browser code later needs a separate cookie host and an isolated worker; a different port alone is insufficient.

### Committee hosting

Jordan's new request establishes committee testing as a concrete reason to revisit the previously deferred hosted track (#44–#46); it does not supply a hosting account, region, IdP, cap or model license. Prepare the real deployment plan/configuration now; choose these exact values at the staging gate using then-current official facts. Do not route committee requests through Jordan's personal Claude/ChatGPT consumer sessions. Use permitted per-user credentials or an explicitly configured eligible server route with quotas. Provide a read-only/sample mode if no runtime route is available and label it honestly.

An initial private deployment may support browsing, files, notes and discovery without claiming build parity. For real committee builds, add a supported isolated hosted execution worker or explicit authorized pairing; do not expose the Windows terminal launcher remotely. Give each tester only their own workspace and seeded public/synthetic examples. Do not copy Jordan's operational database, credentials or unpublished personal files. OIDC, role controls, HTTPS, durable storage, database isolation, preview-host separation, backup restore, reset, quotas, diagnostics, shutdown and a retention policy are release requirements. Keep commerce, campaigns and public registration disabled. Inviting committee members remains a separate messaging action; this task sends no invitations.
