## Verdict

**No High, no Medium.** Every finding from the first review is fixed or reasonably accepted. M-1 is fixed
for the cases it named (workers, nested workers, WebSockets, WebRTC, service and shared workers). Two
narrower gaps remain: popups and anything that happens after a case ends. I rate those Low (L-8). M-2 is
fixed by labelling: every `static-web/1` build is marked as an unqualified trial. The one weakness is that
"qualified" is a global code constant (L-9). Accepting L-7 is reasonable, and the builder's argument for it
is correct (see below). Two new Lows and four nits.

## L-7: is accepting it reasonable?

Yes. The builder's key argument holds. The checker's isolated-world `Runtime.evaluate` calls are
executed by the renderer, so a compromised renderer can return any values the checker grades. It does not
need to ptrace or write to the checker. So the first review's "better fix" (a separate uid or PID namespace
for the browser) would **not** stop a forged pass. Only Chrome's own sandbox plus a trusted browser
process would help, and that needs user namespaces inside bwrap, which is a real design change and
correctly left for its own ADR. (This container has no Yama, so the ptrace part is possible here. On WSL2
it depends on `ptrace_scope`, which doesn't change the conclusion.)

What bounds the risk:

- The exploit stays inside bwrap: no network, a read-only root, tmpfs only, and the systemd unit's limits
  and lifetime.
- The attacker would have to be the builder model, writing a working n-day exploit against a pinned
  Chrome 156 build. Code like that is conspicuous to the independent reviewer, who reads the patch.
- The owner previews the site before relying on it.
- The worst outcome is a false "verified" on a local, $0 build. It is not a credential or host
  compromise.

The remaining weakness is that nothing enforces the "re-check at each slice and at least monthly" update
plan (N-4).

- `score` on the reference gives 10 of 10, with 6 of 6 held out. The sandbox is `bridge.py sandbox_args

- `mutants` catches **all 14 known failures**. Each of the 5 hostile pages (worker request, WebSocket,

- The REAL CHECKER test in `tests/dist/web-recipe.test.js` passes as uid 1000 with the pinned browser.

Weaknesses (nit N-1, plus coverage gaps covered by L-8):

- `mutants()` only checks that a named case fails, not why. Under the **old** checker, `alert-dialog`
  already failed ("The browser did not answer in time") and `native-submit` already failed A3.2
  ("Cannot find context with specified id"). So those two mutants would stay "caught" even if the new
  dialog and navigation detection broke. The worker, WebSocket and WebRTC mutants do pin the new code:
  the old checker passed all three.
- All five hostile edits run at script start, so nothing tests the "after the last step" path or popups.

## New findings

### Low

**L-8. Popups and anything after the case ends escape the outside-request check, and the doc claims
more than that.**

- `web_recipe.py` only watches the checker's page session and its auto-attached children. After the
  last step it waits 0.2 s and reads events once. These passed A1.1 with `outbound: []`:
  - `window.open('http://10.9.9.9/popup')`;
  - `window.open('')` followed by `w.location = 'http://10.9.9.9/p2'`;
  - `setTimeout(() => fetch('http://10.9.9.9/late'), 2500)`;
  - a fetch 600 ms after the first `input` event;
  - `setTimeout(() => confirm('x'), 1500)`.
- Meanwhile `docs/STATIC_WEB_RECIPE.md` §4 says these checks "make the manifest's `network: none` a
  checked claim rather than an assumption". It also says a document load fails the case "even if it
  starts after the last step". That holds only within about 0.2 s.
- The QA sandbox has no network, so there is no QA-time exposure. But the exported package runs in a
  normal browser, and the preview frame already blocks popups (no `allow-popups`).
- Fix:
  - Fail on any new `page` target that has an opener (`Target.targetCreated` with `openerId`, which
    `setDiscoverTargets` already reports).
  - Wait a short, documented settle time (for example 1 s) after the last step before reading events.
  - Reword the doc, the ADR amendment and the manifest limitation to "no outside request was seen during
    the frozen cases". A dynamic check cannot prove a static page never makes one.
  - Add a popup mutant and a delayed-request mutant to the next benchmark version.

**L-9. Recipe qualification is a global code constant, but role qualification is per connection, model
and role prompt.**

- Today this is safe: every web build is labelled. But the documented next step is to add
  `'static-web/1'` to `QUALIFIED_RECIPES` once the benchmark passes live on one connection
  (`packages/contracts/src/web-recipe.ts`).
- From then on, web builds on any other connection, model or role prompt version would carry no trial
  label. That re-creates M-2 for them. PR #75 bound qualification to the current role prompt precisely
  to avoid this.
- Fix: before the constant is changed, derive the label from qualification records keyed by recipe or
  benchmark id for the build's own connection and roles. Or record in ADR-0078 that the constant may
  change only together with such a check.

### Nits

- **N-1.** Make `mutants()` (or the expectations) also match a reason substring for the hostile cases,
  for example "dialog" and "another document", so they pin the new detection (see the benchmark section).
- **N-2.** `docs/STATIC_WEB_RECIPE.md` §3 says "A selector cannot contain `=`". The code refuses only
  ` = ` with spaces, and `[name="x"]` is fine. Also, `selectorShapeOk` falsely refuses a selector that
  ends in an escaped combinator, such as `.a\,` (rare).
- **N-3.** The original ADR-0078 bullets in `tracking/DECISIONS.md` still say `allow-modals` and that a
  new link "ends older frames". The amendment below them supersedes both, but a short "(amended below)"
  would stop the stale reading.
- **N-4.** The L-7 browser update plan has no reminder. Recording the pin date next to
  `BROWSER_VERSION` and having preflight or the build page note when it is older than 30 days would make
  "at least monthly" checkable.

## Checked and fine (beyond the table)

- Worker sessions start paused (`waitForDebuggerOnStart`). `Network.enable`, `Runtime.enable` and the
  nested auto-attach are queued on the session before `runIfWaitingForDebugger`, so the worker's first
  request is recorded. I confirmed this with an immediate fetch from a worker and from a nested worker.
- The WebRTC block runs before page scripts in the main world of every frame, including `about:blank`
  and `srcdoc` iframes. The properties are non-configurable, and page scripts calling the binding can only
  make their own case fail.
- Navigation detection doesn't misfire on hash links (`anchorClick`, same URL), script hash changes, or
  `pushState`.
- Fire-and-forget command ids start at 2^30, so they can't collide with `send()` replies.
- Held-out handling, frame-host path rules and the CSP are unchanged from the first review's "fine" list.
