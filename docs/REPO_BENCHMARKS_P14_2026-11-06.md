# P14 repo benchmarks: small and larger, frozen before any run (November 6, 2026)

This is the preparation half of P14 qualification for the one supported build kind,
`python-build/1` (see the [capability matrix](CAPABILITY_MATRIX_2026-11-05.md), section 3). It
defines one **small** and one **larger** benchmark, freezes their expected results and pass
bars, and gives the exact packet for live runs. **No benchmark was run against the studio or
a model for this document.** The only executions were local checks of the repository's own
reference solutions and deliberately broken copies of them.

Files: `config/repo-benchmarks/` (frozen), `scripts/p14-benchmark.mjs` (checker and scorer),
`tests/src/p14-benchmarks.test.ts`.

## 1. The two benchmarks

|                        | Small: `p14-small-wordtally-v1`                    | Larger: `p14-larger-ledgercheck-v1`                                                                                    |
| ---------------------- | -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Product                | Word tally CLI: top words from stdin, `--top K`    | Ledger cap checker: validates `date,category,amount` rows, totals per category, caps, month filter, text or JSON       |
| Code shape             | One module, `src/main.py`                          | `src/main.py` plus a `src/ledger` package with `parse.py`, `rules.py`, `report.py` (internal API)                      |
| Checks                 | 4 automated checks                                 | 6 automated checks                                                                                                     |
| Studio QA cases        | 10 (6 held out)                                    | 10 (5 held out), the studio's per-build maximum                                                                        |
| Extra held-out scoring | none                                               | 15 extended cases and a structure check, scored after the build on the exported package; never entered into the studio |
| Build caps             | `max_repairs` 1, `max_calls` 4, 4000 output tokens | `max_repairs` 2, `max_calls` 6, 12000 output tokens                                                                    |
| Requests               | typically 2, at most 4 per attempt                 | typically 2, at most 6 per attempt                                                                                     |

"Larger" means more interacting requirements and modules (row validation order, error
precedence, exact money formatting, caps on absent categories, month filtering that still
validates every row, an exact JSON shape) rather than line count. Both are synthetic data.

Each benchmark folder holds:

- `spec.json`: the spec content exactly as it would be entered in the studio. It passes the
  studio's own `SpecContentSchema` and `buildBlockers` (checked by `verify`).
- `expectations.json`: caps, expected requests and cost, attempts, the pass bar, what to
  measure, and the known failure cases.
- `extended-cases.json` (larger only): the out-of-studio held-out suite.
- `reference/`: a reference solution, used only to show the frozen expected outputs are
  reachable. It is never shown to builders or reviewers.

## 2. How the expected results were frozen

1. The spec text and every expected stdout and exit code were written by hand from the spec,
   not generated by the reference solution.
2. The reference solutions were then written separately and scored against them. Both passed
   every case on the first run (small 10/10; larger 10/10 build and 15/15 extended), so no
   expected result was changed after seeing an output.
3. `config/repo-benchmarks/FREEZE.json` records the SHA-256 of every file in both folders,
   with `frozen_before_any_run: true`. `node scripts/p14-benchmark.mjs verify` and the test
   suite fail if any frozen file changes or a file is added. A change means a new benchmark
   version (for example `-v2`), never an edit, and results from the old version stay as they
   are.

## 3. Pass bar and outcome rules (frozen in `expectations.json`)

Per attempt, all of:

- The studio build reaches **verified**: QA passes all 10 frozen cases in the WSL2 isolation
  worker, including every held-out one.
- The independent reviewer approves the final candidate.
- Requests used are within the plan's `max_calls`.
- The exported package, scored by `p14-benchmark.mjs score`, passes all build cases and (larger)
  all 15 extended cases and the structure check.

Each benchmark gets **3 attempts** on the same route, model and role prompts. It is
**qualified at its declared scale** only when all 3 meet the bar; otherwise the result is
recorded as k of 3 and is not qualified. A failed attempt is never re-run to replace it. An
attempt stopped by an infrastructure fault outside the roles (worker crash, studio restart,
plan outage) is recorded with its cause and may be replaced once.

Measured and recorded per attempt: requests and repair rounds used, wall time, files changed
and diff size, reviewer findings, QA development and held-out counts, scorer result, and the
plan's daily request count before and after.

## 4. Scoring a built package

```text
node scripts/p14-benchmark.mjs verify
node scripts/p14-benchmark.mjs score p14-larger-ledgercheck-v1 <export-dir>
```

`score` runs generated code, so by default it runs each case in Bubblewrap with no network, a
read-only copy of the package and a cleared environment (Linux or WSL2, like the studio's
worker). `--runner direct` runs without isolation and is refused unless `--trusted` is given;
that is for the reference solutions or a throwaway container only. It is never for the studio
host with real data. The structure check only parses the source (Python `ast`) and does not
run it.

## 5. Limits found while freezing

- **The studio's QA runs at most 10 cases per build** (`MAX_BUILD_CASES`). The matrix's "15+
  cases" for the larger task cannot all run inside the studio, so the larger benchmark splits
  into 10 studio cases plus 15 extended cases scored afterwards. Raising the limit would be a
  P15 change with its own review.
- **Only builder tasks with no dependencies can be built**, so a multi-task DAG with
  checkpoints cannot be benchmarked yet (P15 slice 3). The larger benchmark is one task
  across several modules.
- **`python3 -I` does not put `src/` on the import path.** Any multi-module product must add
  its own directory to `sys.path` in `main.py`, or every case fails with
  `ModuleNotFoundError`. This was confirmed locally (Python 3.13) and is stated in the larger
  spec as a runtime rule. The builder prompt and template do not mention it today, which
  matters for any future multi-module recipe.
- The held-out cases live in this repository. Runtime roles never see the repository, but a
  coding agent that edits the studio could. That is a limit on any claim about the roles, not
  about coding agents.
